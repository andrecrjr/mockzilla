# Action-Driven Journeys

An application changes state because something happens: a user signs in, an order is paid, or a job completes. A Journey should use those same API requests—not test-only endpoints—to change its state.

## Avoid mock-control endpoints

Do not make the frontend call endpoints such as `POST /set-login-status` or `POST /set-order-state`. They are not part of the production API and hide the behavior a test is meant to prove.

Instead, put the request, state requirement, state transition, and response in one Action:

```text
POST /auth/sign-in
  required state: signed_out
  transition: auth → authenticated
  response: 200 with a token
```

An Action can also write a declared Journey Field—for example, `accessToken`—while remaining explicit. There is no resource layer, effect language, or hidden mutation rule.

## Why it matters

1. The Journey reads like the product lifecycle.
2. Frontend tests call production-shaped endpoints.
3. Resetting declared lifecycle tracks makes replay deterministic.
4. A rejected request can explain the current and required state directly.

Use Handlebars only for declared field values and dynamic response data. Use ordinary folder/subfolder mocks when no previous request needs to affect the result.

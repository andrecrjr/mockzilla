# Journeys

Use ordinary mocks in folders and subfolders for most endpoints. Use a Journey when requests together tell a product story: a customer signs in, pays an order, and follows its delivery.

Journeys are live in the dashboard and API. Create a Journey, add its Actions, run the same endpoints your client calls, inspect the resulting runtime, and reset the story whenever you need to replay it.

## One complete story, several lifecycles

A Journey is standalone. It contains named Lifecycle tracks, each with a visible current state, plus a few declared Fields that carry values through the story.

```text
Customer Journey
├── Authentication: signed_out → authenticated
├── Checkout:      browsing → pending → paid → shipped
└── Delivery:      not_started → tracking → delivered

Fields: orderId, accessToken, trackingCode
```

This lets one API request depend on the part of the story that matters. Paying can require an authenticated customer and a pending checkout, while delivery can stay independent until the order is shipped.

## Business cases that benefit from a Journey

Journeys are most useful when the API must expose a **business decision already made by an earlier request**. They are not limited to consumer checkout.

| Business flow | Lifecycle tracks | Small carried Fields | Requests worth testing in order |
|---|---|---|---|
| B2B purchase approval | `purchaseOrder: draft → submitted → approved → rejected`; `fulfilment: not_ready → queued → dispatched` | `purchaseOrderId`, `approvalCode` | Submit a PO, approve it, then release fulfilment. Verify dispatch is unavailable while approval is pending. |
| Seller onboarding and compliance | `application: started → submitted → under_review → approved`; `payouts: blocked → enabled` | `sellerId`, `reviewReference` | Submit onboarding, receive a review outcome, then create a payout account only after approval. |
| Insurance or warranty claim | `claim: opened → evidence_requested → under_review → settled → denied`; `payment: not_due → ready → issued` | `claimId`, `settlementId` | Open a claim, attach evidence, settle it, then retrieve the payment instruction. |
| Subscription dunning | `invoice: current → overdue → retry_scheduled → paid`; `service: active → grace_period → suspended → restored` | `invoiceId`, `paymentAttemptId` | Fail a renewal, schedule a retry, accept payment, and prove service access is restored. |
| Incident response | `incident: detected → acknowledged → mitigated → resolved`; `communications: quiet → customer_notified → postmortem_sent` | `incidentId`, `statusPageMessageId` | Acknowledge an incident, publish a customer update, resolve it, and prevent a postmortem before resolution. |
| Release governance | `change: draft → submitted → approved → rejected`; `deployment: idle → running → deployed → rolled_back` | `changeId`, `deploymentId` | Submit a change, approve it, deploy it, then test rollback as a distinct, visible state transition. |

### Example: B2B purchase approval

A procurement client often needs to show different UI and API behavior while a buyer waits for approval. Model the decision and fulfilment separately so the test sequence stays understandable:

```text
purchaseOrder: draft → submitted → approved → rejected
fulfilment:    not_ready → queued → dispatched

Fields: purchaseOrderId, approvalCode
```

| Request | Requires | Changes | Why it matters |
|---|---|---|---|
| `POST /purchase-orders` | `purchaseOrder: draft` | `purchaseOrder: submitted`; saves `purchaseOrderId` | The client can show a submitted state and poll the same ID. |
| `POST /purchase-orders/:id/approve` | `purchaseOrder: submitted` | `purchaseOrder: approved`; saves `approvalCode` | Approval is explicit instead of a hidden response variant. |
| `POST /fulfilments` | `purchaseOrder: approved`, `fulfilment: not_ready` | `fulfilment: queued` | A premature fulfilment call receives `409 Conflict`, exercising the buyer-facing blocked state. |
| `POST /fulfilments/:id/dispatch` | `fulfilment: queued` | `fulfilment: dispatched` | The response can render `{{fields.purchaseOrderId}}` and `{{fields.approvalCode}}`. |

Keep PO line items, supplier catalogues, approval-history collections, and fulfilment payloads in ordinary mocks or schemas. The Journey owns only the decisions that make the next request legal or change its response.

## Actions move the story forward

An Action defines:

- its HTTP method and path;
- the lifecycle states it requires;
- the lifecycle states it transitions;
- the declared Fields it writes;
- its status, headers, and response body.

```json
{
  "name": "Pay order",
  "method": "POST",
  "path": "/orders/:id/pay",
  "requires": {
    "auth": "authenticated",
    "checkout": "pending"
  },
  "transitions": {
    "checkout": "paid"
  },
  "setFields": {
    "orderId": "{{params.id}}"
  },
  "statusCode": 200,
  "body": {
    "id": "{{params.id}}",
    "status": "{{state.checkout}}",
    "orderId": "{{fields.orderId}}"
  }
}
```

Mockzilla selects an Action only by method, path, route parameters, and exact required lifecycle states. If none is available, it returns `409 Conflict` with the current state map and the requirements that were not met.

## Keep ordinary mocks ordinary

Folders and subfolders organize independent API endpoints. They remain right for static responses, schema-driven data, request echoing, and endpoints whose response does not depend on earlier requests.

Choose a Journey when this sentence is true: **“This request changes where the customer is in the product story.”**

For a business-facing alternative, read that as: **“This request changes which business operation is now permitted.”**

## Dynamic values: Handlebars only

Journey templates use Handlebars for declared Field writes, response headers, and body. There is no condition language, effect language, or JavaScript escape hatch.

Every response template receives:

```text
request.body
request.query
request.headers
params
state
fields
faker
```

Transitions are declared data, not templates. Mockzilla applies them and `setFields` before rendering the response, so `{{state.checkout}}` can return `paid` and `{{fields.orderId}}` can return the paid order immediately.

## Deliberate limits in v1

Journeys do not include resources, collections, session contexts, arbitrary JSON state beyond declared scalar Fields, condition/effect DSLs, graph editors, or template side effects outside `setFields`. Those features make the engine hard to explain and debug.

Keep lifecycle state and a few carried Fields in the Journey. Keep complex or collection-based response data in ordinary mocks and schemas.
